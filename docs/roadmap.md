# 개발 로드맵

팀 전체가 같은 순서와 완료 기준을 공유하기 위한 문서입니다. 세부 일정은 팀 합의 후 각 Phase에 적습니다.

## 우선순위

| 순위 | 항목 | 발표 비중 |
|---|---|---|
| P1 | 저울 연동 + 실시간 화면 + RMSE | ★★★★★ |
| P2 | Rule Engine (Target Curve 자동 생성) | ★★★★★ |
| P3 | Feedback Loop | ★★★★ |
| P4 | 서비스 화면 | ★★ |
| P5 | Vision (확장) | ★ |

시간이 부족하면 **아래 순위부터** 잘라냅니다. Vision은 설계 문서 + 데모 이미지로 대체 가능합니다.

## 데모 시나리오 (모든 작업의 기준)

최종 발표에서 보여줄 5분짜리 시연을 먼저 고정하고, **여기에 등장하지 않는 기능은 만들지 않습니다.**

| # | 화면 | 보여줄 것 | 필요 Phase |
|---|---|---|---|
| 1 | 원두 등록 | 지역·가공·로스팅 입력 | 0 |
| 2 | 레시피 생성 | 원두량 20 g 입력 → **Target Curve가 즉시 그려짐**. 로스팅을 다크로 바꾸면 곡선 모양이 눈에 띄게 달라짐 | 3 |
| 3 | 추출 | 저울 연결 → 물을 부으면 실선이 점선을 따라 올라감. **RMSE 실시간 표시**, 페이스 인디케이터 | 1, 2 |
| 4 | 맛 평가 | "쓴맛 강함 / 농도 연함" 선택 → **무엇이 왜 바뀌었는지 표로** + 이전 곡선 위에 신규 곡선 겹쳐 표시 | 4 |
| 5 | 히스토리 | 추출 기록 목록, RMSE 추이, "이 레시피로 다시 내리기" | 5 |

시연 성공의 판정 기준은 **3번 화면 하나**입니다. 나머지가 거칠어도 3번이 살아있으면 발표는 성립하고, 3번이 죽으면 나머지가 완벽해도 성립하지 않습니다.

**백업 원칙**

- 데모용 시드 데이터(원두 2~3종, 과거 추출 기록 5건 이상)를 미리 넣어 히스토리 화면이 비어 보이지 않게 합니다.
- **사전 녹화 영상을 반드시 준비**합니다. 라이브 실패 시 즉시 전환.

> **시뮬레이션 모드는 만들지 않습니다.** 시연에서 가짜 데이터를 실측처럼 보여주지 않기 위해서입니다.
> 그 대가로 **라이브 실패 시 대비책이 사전 녹화 영상 하나뿐**이므로, 영상 준비가 선택이 아니라 필수입니다.
> 저울 연동이 끝내 안 되면 그때 시뮬레이션 도입을 다시 논의합니다.

## 배포 (구성 확정, 착수는 교수님 면담 후)

목적은 사용자 확보가 아니라 **기술적 완성도** — 실제로 접근 가능한 형태까지 만들어 두는 것.
시연은 우리 저울로 진행하므로 배포 여부와 무관하다.

**저울을 가진 사람은 배포본으로 전체 기능을 그대로 쓴다.** BLE가 접속자의 브라우저와
그 사람의 저울 사이에서 돌기 때문. iOS는 사파리가 Web Bluetooth를 지원하지 않아 로컬·배포 모두 불가.

### 구성

```
가비아 도메인
   │  A 레코드 → Elastic IP
   ▼
EC2 t3.micro ── Caddy (Let's Encrypt 자동) ─┬─ /       → 프론트 빌드본 (정적)
                                            └─ /api/*  → FastAPI (Docker)
                                                           │
                                                           ▼
                                                   RDS PostgreSQL
```

| 항목 | 선택 | 근거 |
|---|---|---|
| HTTPS | Caddy + Let's Encrypt | **Web Bluetooth가 보안 컨텍스트 전용.** ALB는 월 $16이라 이 규모에 과함 |
| 도메인 | 가비아 | 인증서·OAuth 리디렉트 모두 도메인에 의존. IP로는 인증서 발급 불가 |
| 프론트 | 백엔드와 **같은 도메인** | 분리하면 CORS 설정이 따라옴. 얻는 것 없이 실패 지점만 늘어남 |
| DB | RDS PostgreSQL | 프리티어면 무료. JSON 컬럼(곡선) 처리가 MySQL보다 깔끔 |
| 이미지 저장 | **S3 쓰지 않음** | 아래 참고 |

### 사진은 저장하지 않는다

분쇄도 측정에서 사진은 **입력이지 결과가 아니다.** 측정이 끝나면 쓰이는 것은 `d50Um` 숫자뿐이고,
레시피 계산에도 화면 표시에도 사진은 들어가지 않는다.

```
저장한다   측정 결과 (d50 · 안내 문구 · 원두 · 시각)
버린다     사진 원본  → S3 불필요
```

`GRIND_ANALYSIS.image_path`는 설계 초안에 넣어둔 칸이며 쓰지 않는다.
보관이 필요해지면 EC2 볼륨으로 충분하다. S3는 규모가 커질 때 쓰는 것.

### 착수 시 고쳐야 하는 것

1. **Vite 프록시는 개발 서버 전용.** 빌드본에는 프록시가 없다 → Caddy가 `/api`를 백엔드로 넘긴다
2. **Alembic 도입.** `create_all()`은 기존 테이블을 고치지 않아 운영 DB에 쓸 수 없다.
   소셜 로그인이 `user_id` 컬럼을 추가하는 순간 막힌다
3. **소셜 로그인.** 배포하면 접속자 전원의 기록이 한곳에 쌓여 정확도 추이가 무의미해진다

### 로컬은 SQLite 그대로

`config.py`의 `database_url`을 환경 변수로 덮어쓰면 되고, **코드는 바뀌지 않는다.**

```
로컬   기본값                          → SQLite 파일
배포   DATABASE_URL=postgresql://...   → RDS
```

발표 후 인스턴스를 내려도 로컬에서 그대로 쓸 수 있다.

> Alembic 마이그레이션을 SQLite에서도 돌리려면 손이 간다(SQLite는 `ALTER` 제약이 많음).
> 마이그레이션은 배포용만 관리하고 로컬은 지금처럼 DB 파일을 지우고 다시 만든다.

### 순서

```
도메인 → Alembic → PostgreSQL 전환 → Docker → EC2·RDS·Caddy → 소셜 로그인
```

**도메인이 먼저다.** 인증서와 OAuth 리디렉트가 모두 도메인에 의존한다.

### 정리 계획

발표 후 유지하지 않는다. **인스턴스·RDS·Elastic IP를 함께 해제한다** —
Elastic IP는 인스턴스에 붙어 있지 않으면 과금된다.
