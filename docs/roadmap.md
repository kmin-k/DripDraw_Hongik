# 개발 로드맵

팀 전체가 같은 순서와 완료 기준을 공유하기 위한 문서입니다. 세부 일정은 팀 합의 후 각 Phase에 적습니다.

## 우선순위

| 순위 | 항목 | 발표 비중 |
|---|---|---|
| P1 | 저울 연동 + 실시간 화면 + RMSE | ★★★★★ |
| P2 | Rule Engine (Target Curve 자동 생성) | ★★★★★ |
| P3 | Feedback Loop | ★★★★ |
| P4 | 서비스 화면 | ★★ |
| P5 | Vision (확장) | ★ |

시간이 부족하면 **아래 순위부터** 잘라냅니다. Vision은 설계 문서 + 데모 이미지로 대체 가능합니다.

## 데모 시나리오 (모든 작업의 기준)

최종 발표에서 보여줄 5분짜리 시연을 먼저 고정하고, **여기에 등장하지 않는 기능은 만들지 않습니다.**

| # | 화면 | 보여줄 것 | 필요 Phase |
|---|---|---|---|
| 1 | 원두 등록 | 지역·가공·로스팅 입력 | 0 |
| 2 | 레시피 생성 | 원두량 20 g 입력 → **Target Curve가 즉시 그려짐**. 로스팅을 다크로 바꾸면 곡선 모양이 눈에 띄게 달라짐 | 3 |
| 3 | 추출 | 저울 연결 → 물을 부으면 실선이 점선을 따라 올라감. **RMSE 실시간 표시**, 페이스 인디케이터 | 1, 2 |
| 4 | 맛 평가 | "쓴맛 강함 / 농도 연함" 선택 → **무엇이 왜 바뀌었는지 표로** + 이전 곡선 위에 신규 곡선 겹쳐 표시 | 4 |
| 5 | 히스토리 | 추출 기록 목록, RMSE 추이, "이 레시피로 다시 내리기" | 5 |

시연 성공의 판정 기준은 **3번 화면 하나**입니다. 나머지가 거칠어도 3번이 살아있으면 발표는 성립하고, 3번이 죽으면 나머지가 완벽해도 성립하지 않습니다.

**백업 원칙**

- 데모용 시드 데이터(원두 2~3종, 과거 추출 기록 5건 이상)를 미리 넣어 히스토리 화면이 비어 보이지 않게 합니다.
- **사전 녹화 영상을 반드시 준비**합니다. 라이브 실패 시 즉시 전환.

> **시뮬레이션 모드는 만들지 않습니다.** 시연에서 가짜 데이터를 실측처럼 보여주지 않기 위해서입니다.
> 그 대가로 **라이브 실패 시 대비책이 사전 녹화 영상 하나뿐**이므로, 영상 준비가 선택이 아니라 필수입니다.
> 저울 연동이 끝내 안 되면 그때 시뮬레이션 도입을 다시 논의합니다.

## 확장 검토 (미결정)

아래는 **아직 하기로 정한 것이 아닙니다.** 팀 회의와 교수님 면담을 거쳐 결정합니다.
Phase 6까지 끝나고 시연 준비에 여유가 있을 때만 착수하며, **시연 안정성을 해치면서까지 하지 않습니다.**

### 배포

현재는 발표자 노트북에서 두 프로세스를 띄우는 **완전 로컬 구성**입니다. 시연은 이 방식으로 충분합니다.

배포의 목적은 불특정 사용자 확보가 아니라 **기술적 완성도**입니다 — 실제로 접근 가능한 형태까지 만들어 두는 것.

**저울을 가진 사람은 배포본으로 전체 기능을 그대로 씁니다.** BLE가 접속자의 브라우저와 그 사람의 저울 사이에서 돌기 때문입니다. 시연은 우리 저울로 진행하므로 배포 여부와 무관합니다.

필요 조건: **HTTPS**(Web Bluetooth는 보안 컨텍스트 전용) · Chrome·Edge · 데스크톱 또는 안드로이드.
iOS는 사파리가 Web Bluetooth를 지원하지 않아 로컬·배포 모두 불가합니다.

**착수 시 코드를 고쳐야 하는 부분**

1. **Vite 프록시는 개발 서버 전용입니다.** 빌드본에는 프록시가 없습니다. 프론트 정적 파일을 백엔드가 함께 서빙(같은 도메인)하거나, 따로 배포하고 API 주소를 환경변수로 두고 CORS를 설정해야 합니다.
2. **SQLite는 재배포 시 사라질 수 있습니다.** 대부분의 호스팅이 배포마다 디스크를 초기화하므로, 파일 한 개짜리 DB는 그동안 쌓인 기록과 함께 날아갑니다. → 아래 DB 전환이 사실상 함께 따라옵니다.
3. 로그인이 없어 접속자 전원의 기록이 한곳에 쌓입니다. 사용자별 분리가 필요하면 계정 기능이 별도로 필요합니다.

### DB 전환 (SQLite → MySQL 등)

현재 SQLite는 **파일 하나**라 서버를 따로 띄울 필요가 없고, 로컬 단일 사용자 범위에서 부족한 점이 없습니다.

전환을 부르는 조건은 둘입니다.

- **배포** — 위 2번. 배포하면 사실상 함께 따라옵니다
- **동시 사용자** — SQLite는 쓰기를 한 번에 하나만 처리합니다

전환 비용 자체는 낮게 유지되어 있습니다 — SQLAlchemy를 쓰고 있어 **접속 문자열과 일부 컬럼 타입만** 바뀝니다. 다만 **곡선을 담은 JSON 컬럼**은 DB마다 취급이 달라 확인이 필요합니다.

> 전환한다면 **마이그레이션 도구(Alembic)를 함께** 들여야 합니다. 지금은 `create_all()`로 테이블을 만드는데, 이 함수는 **기존 테이블을 고치지 않습니다.** 스키마가 바뀌면 DB 파일을 지워야 하고, 실제 운영에서는 쓸 수 없는 방식입니다.

**배포 · DB 전환 · 마이그레이션은 따로 검토할 항목이 아니라 한 묶음입니다.**
