# Rule Table (BrewIQ v0.1)

원본: `BrewIQ_RuleTable_v0.1.xlsx` (팀장 로컬 보관, 레포 미포함)
이 문서가 **구현 기준**입니다. 엑셀과 이 문서가 다르면 팀에 알리고 양쪽을 함께 고칩니다.

Rule Engine은 백엔드(`backend/app/services/rule_engine.py`)에 **단일 구현**으로 둡니다. 프론트에 같은 계산을 복제하지 않습니다.

## 1. 입력 / 출력

### 입력

| 변수 | 타입 | 값 |
|---|---|---|
| 생산 지역 | 선택 | 아프리카 / 중미 / 남미 / 아시아·태평양 |
| 가공방식 | 선택 | 워시드 / 내추럴 |
| 로스팅 레벨 | 선택 | 라이트 / 미디움 / 다크 |
| 분쇄 입자 D50 | 실수 (μm) | 카메라(ArUco) 측정 또는 수동 입력 |
| 원두량 | 정수 (g) | 사용자 입력, **10 ~ 30 g** (8-1절, 8-2절 참고) |
| 음용 방식 | 선택 | 핫 / 아이스 → Ratio 자동 결정 |

추출 **후** 입력 (Feedback):

| 변수 | 값 |
|---|---|
| 신맛 | 강함 / 만족 / 약함 |
| 쓴맛 | 강함 / 만족 / 약함 |
| 농도 | 진함 / 만족 / 연함 → Ratio 누적 보정 |

### 출력

| 출력 | 타입 |
|---|---|
| 권장 물 온도 | 정수 (℃) |
| 총 목표 물량 | g |
| 권장 분쇄도 방향 | 텍스트 (상대값, "N단계 굵게/곱게") |
| Target Curve | `(시간(초), 누적 물량(g))` 시퀀스 |
| 아이스 안내 메시지 | 아이스 선택 시만 |

|---|---:|

## 4. Bloom

```
Bloom 물량(g) = 원두량 × 배수
Bloom 푸어 종료 = 10초
Bloom 대기 종료 = 10 + 대기 시간
```

| | 라이트 | 미디움 | 다크 |
|---|---:|---:|---:|
| 물량 배수 | 3.0 | 2.5 | 2.0 |
| 대기 시간(초) | 35 | 30 | 25 |

## 5. 유량 속도

```
유량 = clamp(기본값(로스팅) + 지역 보정 + D50 보정, 2.5, 8.5)   # g/sec
```

| 기본값 | 라이트 | 미디움 | 다크 |
|---|---:|---:|---:|
| | 4.0 | 5.5 | 7.0 |

| 지역 보정 | 전 레벨 |
|---|---:|
| 아프리카 | −1.0 |
| 중미 | 0 |
| 남미 | +1.0 |
| 아시아·태평양 | 0 |

| D50 보정 | 전 레벨 |
|---|---:|
| D50 < 기준 하한 (곱게) | +1.0 |
| 기준 범위 내 | 0 |
| D50 > 기준 상한 (굵게) | −1.0 |

## 6. 주수 배분과 타이밍

```
총 물량   = 원두량 × Ratio
남은 물량 = 총 물량 − Bloom 물량
2차 = 남은 물량 × 0.40
3차 = 남은 물량 × 0.33
4차 = 남은 물량 × 0.27   ← 반올림 오차 흡수를 위해 잔량으로 계산

푸어 시간 합 = 남은 물량 ÷ 유량
주수 간 대기 = (총 추출 목표 시간 − 10 − Bloom 대기 − 푸어 시간 합) ÷ 2
```

| 총 추출 목표 시간(초) | 라이트 | 미디움 | 다크 |
|---|---:|---:|---:|
| | 205 | 185 | 155 |

타임라인:

| 지점 | 계산 |
|---|---|
| 2차 시작 | 10 + Bloom 대기 |
| 2차 종료 | 2차 시작 + 2차 물량 ÷ 유량 |
| 3차 시작 | 2차 종료 + 주수 간 대기 |
| 3차 종료 | 3차 시작 + 3차 물량 ÷ 유량 |
| 4차 시작 | 3차 종료 + 주수 간 대기 |
| 4차 종료 | 4차 시작 + 4차 물량 ÷ 유량 (≈ 총 추출 목표 시간) |

Target Curve는 위 8개 지점을 `(시간, 누적 물량)`으로 잇는 **구간 선형(piecewise linear)** 곡선입니다. 대기 구간은 누적 물량이 유지되는 수평선입니다.

## 7. 검증 예시 (회귀 테스트 기준값)

입력: 원두량 20 g / 핫 / 라이트 / 아프리카 / 워시드 / D50 950 μm

| 항목 | 값 | 계산 |
|---|---:|---|
| 물 온도 | 96 ℃ | 94 + 2 + 0 |
| 총 물량 | 300 g | 20 × 15 |
| Bloom 물량 | 60 g | 20 × 3.0 |
| 유량 | 3.0 g/s | 4.0 − 1.0 + 0 |
| 남은 물량 | 240 g | 300 − 60 |
| 2/3/4차 물량 | 96 / 79 / 65 g | 240 × 0.40 / 0.33 / 잔량 |
| 푸어 시간 합 | 80 초 | 240 ÷ 3.0 |
| 주수 간 대기 | 40 초 | (205 − 10 − 35 − 80) ÷ 2 |

Target Curve:

```
(0,0) (10,60) (45,60) (77,156) (117,156) (143,235) (183,235) (205,300)
```

이 값은 파이썬 참조 구현으로 **전 항목 일치 확인 완료**입니다. Phase 3에서 `pytest` 회귀 테스트로 그대로 고정하세요.

## 8. 결정 사항

### 8-1. 원두량 상한 30 g (주수 간 대기 음수 방지)

**문제**

주수 간 대기는 `(총 추출 목표 시간 − 10 − Bloom 대기 − 푸어 시간 합) ÷ 2`로 계산됩니다.
우변에서 `총 추출 목표 시간`·`Bloom 대기`는 로스팅 레벨별 **상수**인 반면, `푸어 시간 합 = 원두량 × (Ratio − Bloom 배수) ÷ 유량`은 **원두량에 정비례**합니다.
따라서 원두량이 커지면 반드시 어느 지점에서 대기가 음수가 되고, Target Curve의 시간축이 역행해 곡선이 깨집니다.

**임계값** — 최악 조합(핫 · 아프리카 −1.0 · 굵은 분쇄 −1.0 = 유량 최저)

| | 유량 | 1 g당 푸어 시간 | 가용 시간 | 임계 원두량 | 첫 음수 |
|---|---:|---:|---:|---:|---:|
| 라이트 | 2.5 g/s ※ | (15−3.0)÷2.5 = 4.80초 | 205−10−35 = 160초 | 33.3 g | **34 g** |
| 미디움 | 3.5 g/s | (15−2.5)÷3.5 = 3.57초 | 185−10−30 = 145초 | 40.6 g | **41 g** |
| 다크 | 5.0 g/s | (15−2.0)÷5.0 = 2.60초 | 155−10−25 = 120초 | 46.2 g | **47 g** |

※ 라이트는 4.0−1.0−1.0 = 2.0이지만 `FLOW_MIN` 2.5로 클램프됩니다. 클램프가 없으면 임계값이 27 g까지 내려갑니다.
아이스(Ratio 10)는 물량이 적어 라이트 58 g, 미디움·다크는 실사용 범위에서 발생하지 않습니다.

**결정**

입력 원두량에 **상한 30 g**을 둡니다 (`DOSE_MAX_G = 30`).

- 전역 최소 임계값이 라이트·핫의 33.3 g이므로, 30 g이면 **모든 조합에서 안전**합니다 (여유 3.3 g).
- 최악 조합에 30 g을 넣어도 주수 간 대기가 `(160 − 144) ÷ 2 = 8초`로 양수입니다.
- 총 추출 목표 시간과 유량 규칙의 **의미를 바꾸지 않는** 유일한 방안이라 선택했습니다. 대안이었던 **대기 0 클램프**는 "총 추출 목표 시간"이, **유량 역산**은 "유량은 로스팅·지역으로 결정된다"는 규칙이 각각 무너집니다.

**구현**

- 프론트: 원두량 입력을 30 g에서 막고, 상한임을 UI에 표시
- 백엔드: Pydantic `le=30` 검증. 초과 시 `400` ([`api.md`](api.md) 참고)
- 아이스는 58 g까지 안전하지만 **동일하게 30 g을 적용**합니다. 음용 방식에 따라 상한이 달라지면 UI와 검증이 복잡해지고, 30 g 초과는 데모 범위 밖입니다.

**트레이드오프** — 3~4인분(30 g 초과) 추출은 지원하지 못합니다. 데모 범위에서는 수용하고, 다인분 지원이 필요해지면 대기 0 클램프 또는 유량 역산을 재검토합니다.

### 8-2. 원두량 하한 10 g

**결정**: 입력 원두량 하한을 **10 g**으로 둡니다 (`DOSE_MIN_G = 10`).

상한과 달리 **수학적 필요가 아니라 실용적 판단**입니다. 원두량이 작아도 규칙식은 깨지지 않고 주수 간 대기만 길어집니다(7절 조건에서 원두량만 10 g으로 바꾸면 대기 60초). 하한을 두는 이유는 다음과 같습니다.

- 1잔 기준 실사용 최소치가 10 g 내외입니다. 그 미만은 현실적인 레시피가 아닙니다.
- 원두량이 극히 작으면 Bloom 물량도 함께 줄어(5 g·라이트 기준 15 g) 원두를 고르게 적시지 못합니다. Rule Table이 전제하는 추출 모델이 성립하지 않습니다.
- `0`이나 음수 입력을 차단하는 방어선이 필요합니다.

**구현**: 프론트 입력 제한 + 백엔드 Pydantic `ge=10`. 미만 시 `400`.

**재검토 조건**: Phase 1 실측에서 10 g 미만 추출이 유의미하다고 판단되면 완화합니다. 상한과 달리 낮춰도 곡선이 깨지지 않으므로 변경 비용이 낮습니다.

### 8-3. 반올림 규칙

| 대상 | 규칙 |
|---|---|
| 물량 | **정수 g** (반올림) |
| 시간 | **소수 첫째 자리** (초) |
| 4차 물량 | **잔량으로 계산** — `총 물량 − Bloom − 2차 − 3차` |

4차만 잔량 처리하는 이유는 2·3차 반올림 오차가 총합을 어긋나게 하지 않도록 흡수하기 위함입니다.
7절 검증 예시와 일치합니다 — 240 × 0.40 = 96, 240 × 0.33 = 79.2 → 79, 잔량 = 240 − 96 − 79 = **65**.

### 8-4. 농도 피드백의 Ratio 조정 폭

```python
RATIO_STEP = 1.0                           # 1회 피드백당 조정 폭
RATIO_RANGE = {"핫": (12, 18), "아이스": (7, 13)}   # 기본값 ±3
```

- 농도 **연함** → Ratio − 1.0 (물량 감소 → 진해짐) / 농도 **진함** → Ratio + 1.0
- 농도 **만족**은 조정하지 않습니다 (dead zone)

**±1.0을 고른 이유**: 원두량 20 g 기준 총 물량이 300 g → 280 g으로 20 g 변합니다. ±0.5(10 g, 3.3%)는 사용자가 맛 차이를 못 느껴 "안 변했다"고 인식할 위험이 있고, `changes` 표에 `15 → 14`로 정수 표시되는 편이 발표에서 명확합니다. 진동(oscillation) 우려는 dead zone으로 완화합니다.

**상·하한을 둔 이유**: 반복 피드백 시 Ratio가 무한 발산하는 것을 막습니다. 기본값 ±3이므로 각 방향 3회까지 조정 여지가 있고, 데모 시연(1~2회)에는 충분합니다.

**⚠️ 대기 음수 재발 방지 (필수 구현)**: 8-1절의 상한 30 g은 **Ratio 15 기준** 계산입니다. Ratio가 피드백으로 오르면 총 물량이 늘어 임계값이 함께 내려갑니다 — 예: 라이트·핫·유량 2.5에서 Ratio 18이면 임계값이 26.7 g이 되어, 원두량 27~30 g 레시피에서 대기 음수가 재발합니다. 따라서 **Ratio를 올리는 조정은 적용 전에 주수 간 대기를 재계산**하고, 음수가 되면 해당 조정을 적용하지 않고 `notice`로 안내합니다 ("현재 원두량에서는 물을 더 늘릴 수 없어요"). Ratio를 내리는 조정은 항상 안전합니다.

### 8-5. 분쇄도 1단계 = 50 μm

```python
GRIND_STEP_UM = 50
```

기준 범위 폭 200 μm(핫 900~1100)를 4단계로 분할합니다. 수동 그라인더 1클릭(약 30~40 μm)과 전동 그라인더(더 큼)의 중간값이라 특정 기구에 종속되지 않습니다.

**분쇄도는 누적 상태로 저장하지 않습니다.** 시스템이 그라인더를 제어할 수 없으므로 `"2단계 곱게"` 같은 **안내 텍스트만 출력**하고, 다음 추출 시에는 사용자가 입력(또는 Vision 측정)한 실제 D50을 그대로 사용합니다.

### 8-6. 맛 피드백 → 파라미터 매핑 (v0.1)

**문헌 근거가 없는 영역입니다.** 추출 이론상의 방향만 확립돼 있어 조정 폭은 보수적으로 시작하고, Phase 1 실측 후 튜닝합니다.

```python
TEMP_STEP_C   = 1      # ℃
FLOW_STEP_GPS = 0.5    # g/s
GRIND_STEP    = 1      # 단계 (= 50 μm, 8-5절)
TEMP_RANGE    = (85, 96)   # 유량은 기존 FLOW_MIN/MAX 2.5~8.5 유지
```

| 피드백 | 해석 | 물 온도 | 유량 | 분쇄도 |
|---|---|---:|---:|---|
| 쓴맛 강함 | 과다추출 | −1 ℃ | +0.5 | 1단계 굵게 |
| 신맛 약함 | 과다추출 | −1 ℃ | +0.5 | 1단계 굵게 |
| 신맛 강함 | 과소추출 | +1 ℃ | −0.5 | 1단계 곱게 |
| 쓴맛 약함 | 과소추출 | +1 ℃ | −0.5 | 1단계 곱게 |
| 만족 | — | 0 | 0 | 유지 |

**충돌 처리**

- **반대 방향 동시 (신맛 강함+쓴맛 강함, 신맛 약함+쓴맛 약함)**: 과소·과다추출 신호가 공존하므로 **상쇄하고 조정하지 않습니다.** 파라미터가 아니라 **분쇄 입도의 균일성 문제**일 가능성이 높아, 조정 대신 `"분쇄도 균일성을 확인해 보세요"` 안내를 출력합니다.
- **같은 방향 동시 (신맛 강함+쓴맛 약함 = 모두 과소추출, 그 반대 = 모두 과다추출)**: 조정을 중첩하지 않고 **1회만 적용**합니다. 신호가 둘이라고 ±2℃가 되지 않습니다.
- **농도 vs 균형감**: 농도는 `Ratio`만, 균형감은 `온도·유량·분쇄도`만 건드리므로 파라미터가 겹치지 않아 실제 충돌이 없습니다. 우선순위 `농도 > 균형감 > 단맛`은 향후 같은 파라미터를 두고 경합할 때의 규칙으로 유지합니다.
- 모든 조정 후 각 파라미터를 상·하한으로 클램프합니다.

**한계 명시** — 이 표는 실측 검증을 거치지 않은 v0.1 휴리스틱입니다. 발표에서도 "데이터 축적 후 학습 기반으로 전환"을 다음 단계로 제시합니다.

### 8-7. 상수 관리

모든 상수는 `backend/app/services/constants.py` **한 파일**에 모읍니다. 초기값이 문헌 기반이라 Phase 1 실측 후 보정이 예정돼 있고, 변경 지점을 하나로 유지해야 합니다. 코드 곳곳에 리터럴로 흩뿌리지 마세요.
